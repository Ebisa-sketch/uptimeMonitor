Overview            1.1 Purpose              A web application that lets users register HTTP endpoints, checks them automatically on a schedule, records the results, and alerts the user when an endpoint goes down or recovers.            1.2 Users                     Registered user:          creates and manages their own monitors and alert channels.                     Public visitor:          views a public status page (optional feature).            1.3 Architecture                   React single-page application (SPA) for the user interface.                   REST API backend handling authentication, data, and business logic.                   Background worker that executes scheduled checks and sends alerts.                   PostgreSQL database for users, monitors, results, and incidents.            2. Functional Requirements            3.1 Authentication and Accounts                                                   ID                                Requirement                                 FR-1.1                               A user can register with email and password.                                 FR-1.2                               A user can log in and log out.                                 FR-1.3                               A user can reset a forgotten password through an emailed link.                                 FR-1.4                               A user can update their profile (name, email, password, timezone).                                 FR-1.5                               Each user can only see and modify their own data.               3.2 Monitor Management                                                   ID                                Requirement                                 FR-2.1                               A user can create a monitor with: name, URL, HTTP method (GET, POST, HEAD), interval (1, 5, or 15 minutes), timeout (5-30 seconds), and expected status code.                                 FR-2.2                               A monitor can optionally include custom headers, a request body, and a keyword that must appear in the response.                                 FR-2.3                               A user can edit, pause, resume, and delete a monitor.                                 FR-2.4                               Deleting a monitor also deletes its results and incidents, after a confirmation step.                                 FR-2.5                               The system validates URLs and rejects private or internal addresses (e.g. 127.0.0.1, 10.x.x.x).                                 FR-2.6                               A user can assign one or more alert channels to each monitor.               3.3 Check Execution (Backend Worker)                                                   ID                                Requirement                                 FR-3.1                               The worker runs each active monitor at its configured interval.                                 FR-3.2                               Each check records: timestamp, success or failure, status code, response time (ms), and error message.                                 FR-3.3                               A check succeeds only if the status code matches and the keyword (if set) is found within the timeout.                                 FR-3.4                               A failure in one check must not affect any other check.               3.4 Incident Management                                                   ID                                Requirement                                 FR-4.1                               An incident opens after N consecutive failures (default 2, configurable per monitor).                                 FR-4.2                               An incident closes automatically after the first successful check.                                 FR-4.3                               Each incident stores start time, end time, duration, and failure reason.                                 FR-4.4                               Only one incident can be open per monitor at a time.               3.5 Alerts                                                   ID                                Requirement                                 FR-5.1                               A user can add alert channels: email and Telegram (bot token and chat ID).                                 FR-5.2                               A user can send a test alert to verify a channel works.                                 FR-5.3                               An alert is sent when an incident opens and when it resolves.                                 FR-5.4                               No repeat alerts are sent while an incident remains open.                                 FR-5.5                               Alert delivery failures are logged and retried up to 3 times.               3.6 Dashboard and Reporting                                                   ID                                Requirement                                 FR-6.1                               The dashboard lists all monitors with current status (Up, Down, Paused), last check time, and last response time.                                 FR-6.2                               Each monitor has a detail page showing uptime % (24h, 7d, 30d), a response-time chart, recent checks, and incident history.                                 FR-6.3                               Users can filter monitors by status and search by name or URL.                                 FR-6.4                               Check results older than 30 days are purged automatically.               3.7 Public Status Page (Optional)                                                   ID                                Requirement                                 FR-7.1                               A user can mark selected monitors as public and obtain a shareable status URL.                                 FR-7.2                               The page shows current status and 30-day uptime for those monitors only, with no login required.               4. Non-Functional Requirements                                                   Category                                Requirement                                 Performance                               Checks start within about 10 seconds of schedule. Dashboard loads in under 2 seconds. Supports 500 monitors on one small server.                                 Security                               Hash passwords (bcrypt/argon2). Enforce HTTPS. Block SSRF to internal IP ranges. Encrypt alert credentials. Rate-limit auth and API endpoints. Protect against XSS and CSRF.                                 Reliability                               Worker recovers automatically after a crash. One failed check never stops the scheduler. Alerts are retried on failure.                                 Usability                               A first monitor can be created in under 1 minute. Clear error messages. Keyboard accessible with sufficient color contrast (WCAG AA).                                 Maintainability                               Typed codebase, enforced linting and formatting, unit and integration tests for core logic.                                 Deployment                               docker-compose for frontend, API, worker, and database. Environment-based configuration. Database backups.               8. Acceptance Criteria                   A user can register, log in, and create a monitor in under 1 minute.                   When a monitored URL starts returning 500, an incident opens after the configured number of failures and exactly one alert is sent.                   When the URL recovers, the incident closes and one recovery alert is sent.                   Dashboard uptime % matches the underlying stored check data.                   A user cannot view or edit another user&apos;s monitors (API returns 403 or 404).                   Submitting a private IP such as http://127.0.0.1 as a monitor URL is rejected.                   The app is fully usable on a 375 px wide screen.                   Data older than 30 days is removed by the cleanup job.            9.
